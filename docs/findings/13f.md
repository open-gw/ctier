# 13f — the digest identifies the deployment, not the description

13e stopped: two deployments of the same API with different agent
topologies shared a composition digest, so a decision record could
not say which topology was in force. The field was named for what a
deployment consisted of when it was created. 1.4.0 renames it
`deploymentDigest` and widens the inputs. A rename, not a silent
redefinition, so a 0.1.0 record is obviously old.

## Which schemas carried it

| Schema | Carried the field? | Action |
|---|---|---|
| `decision-record` | Yes, as `composition` | `0.2.0`, field `deploymentDigest` |
| `attempt-record` | Yes, as `composition` | `0.2.0`, field `deploymentDigest` |
| `outcome-record` | **No.** Joins a Decision by `correlationId`. | Unchanged, `0.1.0` |
| `conformance-corpus` | Document-level `composition` names the API the cases classify. Not a ledger field. | Unchanged, `0.3.0` |

Decision and attempt moved together. An outcome that identified only
the API while its Decision identified the deployment would have been
worse than either convention. The outcome never had a digest, so it
did not need one invented.

`composition-manifest` and `coverage-report` keep `compositionDigest`.
Those are compose-time artefacts. Compose does not see agent
identities; generating is when they enter.

## The corpus does not assert a digest

No case in this repository — and no `expect` field in
`conformance-corpus/0.3.0` — asserts a digest value. The corpus was
not bumped. That is the good outcome; editing cases would have been
a larger change than this task.

## Four artefacts, one finding

ADR-006's fail-closed floor, C10's record-before-act, the `standard`
profile, and this. Each described the mechanism available at the
time rather than the property it stood for, and each was found by an
implementation rather than by review. The remedy is recorded beside
the criteria maturity note in `spec/validation.md`: it applies to
the specification's own artefacts, not only to its criteria.
