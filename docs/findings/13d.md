# 13d — the standard profile says the wrong thing

`standard` assumed an authorisation server that enforces scope
reduction at token exchange. 13b showed that Keycloak 26.3.3 does
not: re-exchange restored a scope the reduced token did not carry,
because the client was still entitled to it. 13c showed that the
same product *does* bound an exchange by the requesting client's
entitlement, and that the bound is expressible in imported realm
JSON. 1.3.0 names that mechanism. An implementation that claimed
`standard` under the old wording would be claiming something
different under the new. That is why this is a minor bump, not a
patch.

## Part 2 — the criteria

C1–C12 were read. **None of them states delegation in lineage
terms.** No criterion says the token carries no more than the token
it was derived from, or anything like it.

C1 is precedence of classification over routing. C2 is fail-closed
on an undeclared operation. C3 is unidirectional escalation. C4 is
the human out of the request path. C5–C10 are the withheld
response, persisted execution, derived keys, expiry versus
rejection, no Tier 4 resume, and that a decision precedes the act.
C11 is an injected tier. C12 is binding to the deployed revision.

Delegation appears in the profile dimension, in the README's list
of runtime remainders, and as an `escalationReason` enum value. It
does not appear as a criterion. That is the good outcome: the
criteria were written as properties rather than mechanisms, which
is what 11a concluded C10 should have been. No criterion is edited
in this task.

## Part 4 — the schemas

No schema in `spec/schemas/` encodes what `standard` means. The
corpus schema's `profile` field is an enum of two names,
`standard` and `constrained`, with no description of either
mechanism. The record schemas carry
`delegation-authority-expansion` as an escalation reason; they do
not define how an exchanged token is bounded. Nothing needed a
version bump. The profile was a name, not a shape.

## The same finding, past the criteria

Three profile-or-criterion descriptions have now had to be
corrected after something was built against them: ADR-006's
fail-closed floor, C10's record-before-act, and this. Each
described the mechanism the author had in mind rather than the
property being protected, and each was found by an implementation
rather than by review. That is the same finding as the criteria
maturity note, and it now extends past the criteria.
