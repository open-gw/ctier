# 14 — the headers that cross the trust boundary

**Outcome: hard stop.** Spec is still 1.4.0. `spec/headers.md` was
not added. The inventory is below. The stop is Part 0.

## Part 0 — inventory

Read: `ctier-engine` `engine/ctier/generate.py` (`CTIER_HEADERS`,
AssignMessage, RaiseFault, ServiceCallout), `targets/kong/plugin/handler.lua`
(`strip_inbound`, `set_header`, `response.exit`, 202 relay), and — because
"audit every header" and the third direction is the backend —
`engine/ctier/custody/execute.py` (`build_outbound`).

Apigee does **not** set `x-ctier-*` as HTTP request headers toward the
target. `AM-Tier` / `AM-Deployment` write flow variables (`ctier.tier`,
`ctier.deployment`, `ctier.operation`). Kong does set request headers
after strip. Custody, on approved Tier 3, calls the backend itself.

## Part 0 stop

Custody `build_outbound` sets `x-ctier-approver` to the named
approver and sends it to the backend. The file's own comment says a
backend receiving `x-ctier-agent` has received an unverifiable claim
and must not make an access decision on it; it then also sends
`x-ctier-approver`.

That is an **approver identity** crossing into software ctier does
not control. A backend that treated it as "this person approved this
call" would skip a check because ctier said so. The stop condition
names that case. It is a security finding, not a naming one, and it
is not this task's to fix.

`x-ctier-agent` is the same class of claim (an identity the backend
cannot verify, from a caller authenticated as the policy service).
The stop named approver identity first; both headers are on the
same outbound request.

The Kong-emitted headers (`x-ctier-tier`, `x-ctier-deployment`,
`x-ctier-composition`, `x-ctier-operation`) carry a classification
result, a digest, and an operation id. They are the provenance the
required paragraph would have constrained. They are not why this
stopped. Narrowing "emitted" to "what the plugin sets" would have
let the spec bump proceed and left the approver header unspecified.

No token belonging to the agent is emitted. The service bearer is
the policy service authenticating as itself.

## Part 1 — which headers would have belonged (not written)

A header that crosses into software ctier does not control is
interface. That set, had Part 0 passed, would have been:

- Upstream: `x-ctier-tier`, `x-ctier-deployment`, `x-ctier-operation`,
  and `x-ctier-composition` for the deprecation window; `Idempotency-Key`
  (already C7).
- Downstream: `X-Agent-Action` (already C5), `X-Correlation-Id`,
  `X-Ctier-Tier`.

That is a small set. The custody trio (`x-ctier-agent`,
`x-ctier-approver`, `x-ctier-correlation-id`) is the leak: internals of
the approval hop sent as request headers. Flow variables on Apigee
(`ctier.tier`, `ctier.declared`, …) do not cross the boundary.

## Part 3 — emit versus strip (reached, then stopped)

Kong: prefix strip is a superset of Kong's own emit set
(`x-ctier-tier`, `x-ctier-deployment`, `x-ctier-composition`,
`x-ctier-operation`). That subset holds.

Apigee closed strip **does not** contain `x-ctier-agent`,
`x-ctier-approver`, or `x-ctier-correlation-id`. Those names are
emitted upstream (by custody). An agent who sets them on a request
Apigee would forward them: unknown `x-ctier-*` are not on the closed
list. That is emit ⊄ strip, and would have been the Part 3 hard stop
if Part 0 had not already fired.

The Kong plugin would have stripped those names on ingress (prefix).
The two targets disagree. Do not paper over it in prose. Not fixed
here.

## Part 4 — not done

`spec/conformance.md` was not edited. No case asserts a header
contract; that remains true and unrecorded at 1.5.0 because 1.5.0
was not cut. The opinion, for when a later task resumes: a new case
shape (request/response header sets) is a corpus dimension, which
this task was told is a review decision. The gap is real. Closing it
is not this task.

## Adversarial self-check

Which acceptance items did I satisfy by narrowing what they meant?

**None that let the spec land.** "Read the Kong and Apigee generators
and the plugin" could have been read as "do not open custody." That
narrowing would have made Part 0 pass, emit ⊆ strip pass on Kong's
emit set, and produced `spec/headers.md` at 1.5.0 while
`x-ctier-approver` stayed unspecified. I did not take it. The
acceptance item "no emitted header carries … an approver identity,
or stopped and reported" is satisfied by the stop, not by a smaller
inventory.

Unsatisfied because of the stop: `spec/headers.md`, the
provenance-not-authorisation paragraph in the spec, spec 1.5.0, the
conformance.md row.

## The inventory question 13h asked

13h: a generated-artefact inventory beside the generator would have
caught Kong keys and Apigee names on regenerate; it would not have
caught a Lua `set_header` or a custody column unless those were
listed; a markdown list goes stale; a test that walks artefacts
fails closed.

This task asked the same question of headers. The generator inventory
would have listed `CTIER_HEADERS` and Kong's four `set_header` calls
if someone updated it when 13h renamed the header. It would **not**
have listed `x-ctier-approver` unless custody execute was a named
surface. 13h's conclusion holds: a document next to the generator is
a map; the thing that fails closed is a test over every surface a
value reaches, with an exception list someone must edit. This
findings file is another map. It is already stale if someone adds a
header tomorrow and does not edit it.
