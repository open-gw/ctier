# 06b — define the bound comparison

## How the gap surfaced

06a implemented bounds escalation on the Apigee target as a declarative
numeric condition. The engine's `exceeds_declared_bounds` used Python
`int()`. The two disagree on values such as `101.0` and `1e2`: `int("101.0")`
raises, so the engine does not escalate; Apigee's `>` accepts a decimal, so
it does. 06a recorded that as an expressiveness limit of Apigee's condition
syntax.

It is not. `spec/extensions.md` and `spec/validation.md` said that `max` is
an integer and that `parameter` must name a parameter on the operation. They
did not say what the comparison means when the request value is not an
integer. Two implementations read the same specification, reason reasonably,
and differ. That is a specification bug found by implementation.

A divergence marker in the conformance corpus would be a per-target fork
under another name. 08b.1 established there are none. The comparison is
defined here so 06c can make the engine match it, rather than the corpus
absorbing two readings.

## The reading

The comparison is decimal-numeric. `101.0` and `1.01e2` both exceed a `max`
of `100`. A value that does not parse as a decimal number does not escalate.
A request that omits the parameter does not escalate. Neither is an error.
`max` remains an integer; the schema is unchanged.

Integer parsing was the other available reading, and it fails open:
`int("101.0")` raising means a request that exceeds its bound proceeds at
the unescalated tier. Of the two readings, one fails open and one fails
closed. The specification does not leave that to interpretation.

No schema change. Shape was never the problem.
