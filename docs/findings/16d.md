# 16d — requirement 3 is a property with a declared bound

Spec **1.7.0**. 16a stated requirement 3 as a flat operator duty:
fragment mode cannot guarantee strip-before-read, on any of three
gateways. 16b then passed precedence on APISIX by concatenating in
the same plugin slot. 16c showed that pass was not general (E1),
and that Kong can pass against a bounded class of readers (E2).
Only the third statement is true: an implementation can guarantee
the property for a class of coexisting configuration, and the class
differs per target.

## The restatement

Requirement 3 is now the property (the strip precedes any reserved-
header reader) plus the obligation to declare a class, including
what the class **excludes**. The deployment remains responsible
outside it. Kong's 10000 and APISIX's slot condition stay out of
normative text: they are implementation facts that change with a
plugin release. The specification requires that an implementation
publish its bound; where it publishes it is its own business.

A bound stated only positively will be read as complete.
"Conformant against readers below 10000" excludes `pre-function` at
1e6 — the component a team is most likely to use to read headers
for its own reasons. Coverage without exclusion is not a
description.

## Part 4 — surrounding text that assumed universality

1.6.0 was written when requirement 3 held nowhere in fragment mode.
Wording leftovers, none of them criteria:

- `spec/headers.md` said the order "is not free" wherever
  configuration coexists. Restated: the deployment owes requirement
  3; an implementation that guarantees a class MUST declare it,
  including exclusions.
- `spec/README.md` 1.6.0 changelog said fragment mode "does not, on
  any of three gateways tested." Left as the 1.6.0 historical
  claim, qualified "as then measured." 1.7.0 is the restatement.
- `spec/conformance.md` called Kong and APISIX fragment mode "not
  C11-conformant" as a general result. That used C11 as a stand-in
  for plugin order, which 16a declined to do, and it was not true
  after 16c. Reworded: classification 24/24 stands; precedence is
  estate-dependent and named in the table.

**No criterion edited.** C11 remains the injected-tier rule.

## Evidence

The table in `spec/conformance.md` names the estate. After E1 a row
that says "APISIX fragment: precedence passed" without an estate is
neither reproducible nor generally true.

## The observation

Requirement 3 has now been stated three ways in eight days: *we
cannot guarantee this* (16a), *we can, on APISIX* (16b), *we can
within a class that differs per target* (16d). Only the third is
true, and it was reachable only after two experiments that each
looked like a conclusion.

The pattern is not that the earlier statements were careless. It is
that a guarantee about coexistence cannot be settled by reasoning
about one configuration, and the first configuration anyone builds
is the one that makes their design look right.

## NEW-MATTER

"State what it excludes" is a general drafting rule and this is its
first appearance. It belongs on any claimed class of coexisting
configuration. It is not pasted onto other criteria in this pass:
C10 already requires stating which mechanism a deployment relies
on, which is coverage, not exclusion. Whether other claimed bounds
in the specification should grow the same exclusion sentence is a
later drafting pass, not a criterion expansion.
