# 12b — promoting the corpus and the record schemas

The engine still reads these formats from `ctier/spec/draft/`. After it
vendors 1.2.0 it should read them from the vendored `spec/schemas/`
like every other schema, and the drift manifest should cover them.
That is an engine change. This task does not delete the drafts.

The `ctierSchema` strings also change. The drafts were
`conformance-corpus/0.3.0-draft`, `ledger-decision/0.1.0-draft`,
`ledger-attempt/0.1.0-draft`, `ledger-outcome/0.1.0-draft`. The
normative values drop `-draft` and rename the records:
`decision-record/0.1.0`, `attempt-record/0.1.0`,
`outcome-record/0.1.0`. Version numbers are unchanged. The engine's
writers still emit the draft strings until that vendor bump.

## What a test directory had hidden

A schema read only by the code that writes it can carry the name of
the store it sits in. The drafts were `ledger-*` because they lived
next to a SQLite ledger. Promotion names them as documents, which is
what ADR-009 said they were. The filename and the `ctierSchema` const
now match the other artefacts (`coverage-report/0.1.0`, not
`sqlite-coverage`). That rename is not a semantic change and would
have been invisible for as long as only the writer read the file.

The corpus field for the C13 digest is `composition`, not
`compositionDigest`. Every other promoted document uses
`compositionDigest`. The generator wrote `composition`; the draft
schema checked that key; promotion kept it. Changing it here would
have been a silent break of every corpus the engine has ever dumped,
made in the name of consistency by a reader the writer never had.
Leave it. The second implementation will notice, and that is the
point of publishing.

`additionalProperties` stayed `true` on the corpus (unknown fields
MUST be ignored) and `false` on the three records (an extra column on
a ledger row is a different claim). The drafts already split that way.
Promotion did not invent it; putting the four files next to
`coverage-report` made the split visible.
