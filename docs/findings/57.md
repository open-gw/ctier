## The distinction this task
exists because of

Ask: what is each class's
obligation?

| Class | Owes |
|---|---|
| Criterion | a requirement |
| Response identifier | a definition: meaning, when emitted, what a caller may conclude. A requirement may attach (C5: MUST NOT retry). The baseline is the definition |
| Record field | both, probably: a requirement on the writer, a definition a later reader can apply |
| Disposition | both |
| Escalation reason | a definition |
| Measurement kind | a definition |
| Header | a requirement |
| Validation rule | a requirement |

Population A's remaining
split uses this, not a
second requirement-sentence
pass. `execute`,
`refuse-and-suspend`, the
six escalation reasons, the
ledger fields, Configured
and Observed, outcome
`executed` / `failed`:
definition first. Some will
also need a requirement.
Do not discover that by
asking only whether a MUST
sits beside the name.

## Part 3 —
`provisioning_defect`

Specified. Not by default
because it exists.

The condition is real: a
classified operation this
deployment cannot enact.
Level 2 has no custody, so
Tier 3 cannot withhold. An
excluded operation a live
token reached is the same
disposition in the
reference. The ladder
already named the outcome
(`refuse-provisioning`).

No existing
client-observable
identifier covers it.
`pending_authorization`
would mean something is
pending; nothing is.
`agent_suspended` would
mean a Tier 4 handover;
this is not C9.
`unassigned` is C12's miss,
already on the wire under
its own name. `refuse-provisioning`
is the ledger disposition;
a client does not see it.
The split is the same as
`withhold` /
`pending_authorization`.

Not removed. This is a
governance outcome, not an
operator error to keep off
the wire. Same
`agentAction` as a
withhold, which is why the
`status` is the
discriminator.

47: the specification
mints the format; an
implementation proposes.
This pass minted.

C12's English "provisioning
defect" is the unassigned
miss, not this token. The
criterion is unaltered.

## Part 5 — closed

The set is closed. An
implementation MUST NOT
emit a `status` or
`agentAction` this
specification does not
list. When it needs a
condition the set does
not cover, it proposes.
It does not mint.
`provisioning_defect` is
the evidence that happens
when the rule is unstated.

A client that receives an
identifier it does not
recognise MUST NOT retry
and MUST NOT stay
engaged. Fail-closed for
the agent. Not a
definition of a new
identifier.

Additive evolution is the
same question on a
different surface, and
the answer is not the
same. Unknown *keys* on a
document: ignore, in a
named extensions object.
Ledger records: closed.
Unknown `x-ctier-*`
headers: strip (C16).
Unknown *values* of
`status` and
`agentAction`: this rule.
Ignoring an unknown
status would be
fail-open.

## What the engine now has
to change

Report only. This
repository does not edit
the engine.

- Do not mint a further
  `status` or `agentAction`.
  Propose.
- Keep emitting
  `provisioning_defect`.
  It is specified. Do not
  rename it to
  `refuse-provisioning`.
- `halt`, `unassigned`,
  `custody_unavailable`,
  `unauthorized` are
  specified. Kong already
  emits them. No generator
  change for those names.
- APISIX `_UNAUTH_BODY` is

  recorded the bound; it

  to grow a body.

  carries `agentAction`.
  APISIX `fault-injection`

  header. Kong unassigned

  mechanism requires the
  header; C9's `423`
  mechanism requires it
  on Tier 4. The miss
  paths were not those
  mechanisms. Named.
- C9's named mechanism
  carries `incidentId`.
  Neither live engine
