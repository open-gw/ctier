# 24 — what does C7 actually require?

Spec **1.8.0**. Requires engine 22 and 23. Did not declare C7
level-dependent. Did not scope the 1.5.0 header MUST.

## Part 1 — the current text, classified

As of 1.7.0, C7 read:

> **C7 — Idempotency keys are derived, not generated.** Derived from
> the declared `operationId` (or method + path template) plus a
> canonical serialisation of the request specifics, so a
> resubmission resolves to the pending context rather than creating
> a second one.
>
> Request specifics for the purpose of derivation are the **request
> target, query, body, agent identity and task identity**. Headers
> are not included. A derivation that includes a credential produces
> a key that changes when the credential rotates, which defeats the
> guarantee.
>
> The derived key is transmitted to the target in the
> `Idempotency-Key` request header. An inbound `Idempotency-Key` or
> `X-Idempotency-Key` is agent-supplied and MUST NOT reach the
> backend. The key the target sees MUST be the derived one, on
> every request that reaches it, not only on custody's execute path.
>
> The key is derived once, when the operation is first classified,
> and stored with the persisted context. It is **not** re-derived at
> execution time. …

**It names a mechanism.** The title is how the key is made. The
body is inputs, a header name, when to compute, and a MUST that the
target see that derived value on every request. "A resubmission
resolves to the pending context rather than creating a second one"
is the property the mechanism was standing in for, buried in a
purpose clause. That is C10 before 1.1.9.

## Part 2 — the restatement, and what dropping "derived" newly permits

1.8.0 states the property: **a duplicate attempt MUST NOT produce a
second execution.** Same declared identity, target, query, body,
agent, and task, submitted twice or applied twice, executes once.
Derivation remains one way to satisfy it. An implementation MUST
state which it relies on.

Dropping "derived" without a further clause would permit an
agent-supplied `Idempotency-Key`: one agent choosing a value that
a honouring backend treats as a duplicate of another agent's
operation. That is why ctier derives rather than accepting the
header. A property-only restatement that said nothing about who
supplies the identifier would be weaker than the mechanism it
replaced.

The closing clause, as property not mechanism: **no party can cause
another party's operation to be suppressed by choosing the
identifier a honouring backend uses to recognise a duplicate.** An
inbound `Idempotency-Key` is a choice by the requesting agent. It
MUST NOT be that identifier.

What stays from the old letter, now attached to the derivation
mechanism rather than to the criterion: headers including
credentials are not part of the operation's identity; a derived key
is computed once at classification, not at execute; the wire name,
if a header, is `Idempotency-Key`.

The 1.5.0 MUST that every backend request carry a derived key is
not restated here and not scoped. It lives in `headers.md` and
waits.

## Part 3 — candidates at Level 2

None of these is implemented.

| Candidate | Verdict |
|---|---|
| Derivation at the enforcement point | **Ruled out by 22.** The Python function hashes the body (canonical JSON, else raw). Agreeing on a canonical form for arbitrary bodies, across two languages, at request time, is not tractable. The abandoned Lua join agreed on the empty GET and diverged on JSON order, whitespace, unicode, and quoted query values. A happy-path match would have certified a split key space. |
| An agent-supplied key namespaced by a ctier-supplied identifier | **Not shown to satisfy.** Cross-agent collision is impossible only if the partition is unforgeable (an authenticated subject, not `X-Agent-Id`) **and** the backend treats the partition as part of the identifier, not a decoration it may ignore. ctier would have to send that partition; the backend would have to refuse to honour the agent suffix alone. That is a new backend contract, not an enforcement-point setting. **Tension with 14a, not resolved here.** 14a removed unauthenticated headers that asserted who approved. A namespace would be ctier's own assertion, stripped on ingress, used to partition a key space rather than to authorise. Whether that difference is sufficient is the author's call. |
| Dedup on something ctier already sends | **No.** `x-ctier-correlation-id` is minted per attempt: stable per request, not across a retry of the same operation. Dedup on it would never collapse a retry. `x-ctier-operation` is stable per operation class, not per body: dedup on it would collapse distinct bodies onto one key (the Apigee failure). `x-ctier-deployment` is per deploy. Nothing already on the wire is the operation identity C7 names. |
| Nothing (enforcement point, no custody, no new backend semantics) | **This is the Level 2 answer.** Strip the agent's key; emit nothing. Missing protection fails open. That is what the reference does after 23. |

## Part 4 — the property at Level 2, without a level rule

The property is **not** satisfiable at Level 2 by any candidate that
does not require new backend behaviour. Namespacing remains a
candidate for a later task; it is not available at the enforcement
point alone.

No level-dependence is declared. No rule is added to the
specification. Draft for the author, to take or reject in its own
task:

> A criterion MAY be declared level-dependent only where no
> mechanism available at that deployment level can satisfy its
> property — not where the known mechanism is merely difficult.

Without that guard, level-dependence becomes the escape hatch for
every criterion someone finds inconvenient. Derivation at the
gateway is difficult (22). It is also the known mechanism. Difficulty
is not the test the draft names.

## Part 5 — still pending

`headers.md` still carries 1.5.0's MUST that every execute present
a derived `Idempotency-Key`. Its wording depends on this restatement
and waits.

## The observation

C7 named a mechanism. That is the sixth artefact in this project to
do so, and the first found by asking rather than by building. Every
previous one surfaced because an implementation ran into it. This
one surfaced because a task asked *what does this criterion actually
require* before assuming the answer. That is cheaper, and it is a
method, not a coincidence.

The defect is therefore not universal in the criteria that were
written well by accident — C7 was not one of those. What was
different about C10's 1.1.9 restatement is that building had already
forced the question. What is different here is that 22 forced the
question before another target implemented the letter.

## NEW-MATTER

Whether a criterion MAY be declared level-dependent, under the
guard drafted above. Whether namespacing's difference from 14a is
sufficient. The 1.5.0 header MUST, now that C7 is a property.
