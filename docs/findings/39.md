# 39 — the four mixed criteria

Spec **1.13.0**. Requires 25. Independent of 38. C1, C7, C10
and C12 were not edited. Engine behaviour was not changed.

25 classified C5, C6, C9 and C11 as mixed. Each is restated
below with its own permit-question. None was worse than
mixed. None was left unchanged.

---

## C5 — what loosening newly permits

The title was a property. The body prescribed a status, a
field list, and a constructor. Protected property: a
withheld agent does not retry and does not stay engaged.

Dropping the `202` field list without a further clause
permits a response that ends the exchange and tells the
agent nothing — a `204`, an empty `202`, a status that
stops retries by being unclassifiable. The agent halts, or
guesses. That is not the withheld disposition. The withheld
disposition releases the agent *onto the rest of the task*.

Closed **inside C5**: the response MUST be terminal, MUST
NOT invite retry of this step, and MUST instruct the agent
to continue the rest of the task without this step.
Silence that merely stops the agent does not satisfy.

The `202` field list, `X-Agent-Action`, and
policy-service construction remain one way. A compiled
body and another non-retryable status that carries the
instruction also satisfy. An implementation MUST state
which it relies on. The no-URL rule is unchanged.

`authority` and `expiresAt` stay attached to the named
mechanism. They serve the review, not the agent's
release.

---

## C6 — what loosening newly permits

Two properties in one criterion: the bytes that execute
are the bytes that were approved, and the agent is not
the client. "Persisted context" named a store. 25's
alternative was a signed snapshot the agent never
resubmits.

Dropping "persisted" without keeping both halves permits
either hole. An agent that presents the approved bytes
satisfies byte-identity and is still the client. A later
submission that happens to match is not the approved
bytes, even if a store is no longer named.

Closed **inside C6**, both clauses: those bytes MUST be
the bytes that were approved, not reconstructed from a
later submission; and the agent is not the HTTP client of
the execute. Loosening the store does not loosen either
half.

Persist-and-execute under the policy service's identity
remains one way. A signed snapshot the agent never
resubmits, executed by a party that is not the agent, is
the other named way. An implementation MUST state which
it relies on. The credential carve-out is unchanged.

## C9 — what loosening newly permits

The first sentence was the property. The rest named a
status and a field list. Protected property: a Tier 4
operation does not execute as the agent.

Dropping `423` without a further clause permits resume
under a derived identity — a service token minted from
the agent's credential, a delegation that is the agent
in all but name. The operation "executes under the
policy service" and the agent is the policy service.

Closed **inside C9**: no state transition exists by which
a Tier 4 operation executes under the agent's identity,
**or under an identity derived from it**. A service
identity minted from the agent's token is the agent's
identity in all but name. The human performs the
operation under their own credential.

The `423` field list remains one way. Another response
that names no resume handle and instructs halt-and-hand-off
also satisfies. An implementation MUST state which it
relies on. No correlation identifier stays as property:
a handle the agent can watch is a resume path. The
no-URL rule is unchanged.

---

## C11 — what loosening newly permits

The honour-rule was already in the text: a tier arriving
as an inbound client header MUST NOT be honoured. Strip
or integrity-protection were already named as
interchangeable. What the letter still did was lead with
the trust-boundary frame and MUST the two mechanisms
rather than require an implementation to state which.

Dropping strip-or-MAC without a further clause permits
compile-and-never-read (already how the compiled targets
classify — intended) and also forward-without-strip (the
enforcement point ignores the header and the backend
sees it). Honouring means treating the inbound value as
the assigned tier. Forwarding is not honouring *at the
enforcement point*.

The honour-rule is closed **inside C11**. The
forward-without-strip hole is not this criterion: the
namespace strip remains independently required by
`headers.md` (1.5.0) and is not restated here. Plugin
order is requirement 3. 16a declined to fold either
into C11; this restatement does not reverse that.

Strip, integrity-protection, and a deploy-time binding
that never reads an inbound tier header are named ways.
An implementation MUST state which it relies on.

### Scope-dependence, the way 38 asks about C12

38 asks whether C12's "reachable" means through the
gateway or through a path ctier governs. That scope
decides whether the reference satisfies C12. C12 shipped
without it.

C11's property is "the agent does not choose its tier."
After 1.5.0 the strip that keeps an injected name off
the path is the namespace strip, bounded per target
(16c): Kong against readers below 10000, APISIX only
where a reader shares the strip slot. That bound is
requirement 3's class of coexisting readers. 16a and
16d kept it out of C11.

Does the honour-rule depend on that strip? On a
compiled route, classification uses the compiled
assignment and does not read inbound `x-ctier-tier`.
Test 1 does not fire for the honour-rule: an injected
`x-ctier-tier: 1` on a compiled Tier 4 is `423` (08c,
17). The 16c bound is about other components reading a
reserved header before the strip. That is requirement 3,
not whether the enforcement point honours an injected
tier.

C11 already names its boundary: the enforcement point
does not honour. An unknown estate route is outside
that point — the same family of question as 38, and
already answered by the title 25 quoted. C11 did not
ship without a scope. It is **not** scope-dependent the
way 38 asks about C12. Not a stop.

## The number that closes the audit

25 classified ten criteria: **two mechanisms** (C1, C12),
**four mixed** (C5, C6, C9, C11), **four properties**
(C2, C3, C4, C8). C7 had already been restated (1.8.0).
C10 had already been restated (1.1.9).

26 reduced the mechanisms to one: C1 was misclassified
as a restatable mechanism, because "recorded" *was* the
property. 27 restated C12. This task settles the mixed
count.

**All four were genuinely mixed.** The property was in
the text. Loosening opened a hole; a clause inside the
same criterion closed it. None was fine as written —
C11 already named two mechanisms, but it MUSTed them
and led with the trust-boundary frame, and it did not
require an implementation to state which. Mixed count
does not drop. A smaller number would have been more
honest; it was not available.

Of twelve criteria, **seven** stated a mechanism where
a property was meant:

| Criterion | Class | Where restated |
|---|---|---|
| C5 | Mixed | 1.13.0 |
| C6 | Mixed | 1.13.0 |
| C7 | Mechanism | 1.8.0 |
| C9 | Mixed | 1.13.0 |
| C10 | Mechanism | 1.1.9 |
| C11 | Mixed | 1.13.0 |
| C12 | Mechanism | 1.12.0 |

C1 does not make eight. 26 stopped: the word that
looked like a mechanism was the property. C2, C3, C4
and C8 were already properties.

Seven of twelve, found by asking. That is the
artefact-level answer. It is not a universal drafting
failure and it is not an accident concentrated in one
era: C12 is the compiled architecture written as a
location; the four mixed are the C5 shape 09a already
described; C7 was found by asking before another
target hit the letter; C10 was leftover of a
request-time write.
