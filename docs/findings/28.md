# 28 — the derived-key MUST follows the mechanism

Spec **1.9.0**. Requires 24 and 25. Independent of 26 and 27.

## The rewritten requirement

An implementation that satisfies C7 by derivation MUST emit the
derived key on every execute, under `Idempotency-Key`. An
implementation satisfying C7 by another mechanism states that
mechanism instead, and this requirement does not apply to it. An
inbound key remains agent-supplied and MUST NOT reach the backend.

The requirement is not scoped by deployment level. Level 2 in the
reference lacks the key because it lacks the mechanism.

## The ladder entry as landed

> Level 2 enforces Tiers 1, 2 and 4 with no ctier runtime component.
> It does not satisfy C7: duplicate execution under ordinary agent
> retry is not defended against at this level.
>
> A mechanism was available — an agent-supplied key namespaced by a
> ctier-supplied identifier, so that no agent can suppress another's
> operation — and was declined, because it would place an identity
> value on the request that ctier had removed for separate reasons.
> An implementation willing to make that trade could satisfy C7 at
> Level 2.

The same paragraph sits under What ctier requires of the
deployment. The spec did not previously carry the ladder; 1.9.0
adds it so the exclusion is where a reviewer looks, not only in
findings.

would catch next. Task 26 already opened it.

## The observation

This is the first requirement in the specification whose
applicability depends on which mechanism an implementation
declares, rather than on what it is or where it runs. That is a
direct consequence of restating criteria as properties: once a
criterion admits several mechanisms, the requirements attached to
any one of them have to say which they belong to.

Expect more of this shape as C1 and C12 are restated. It is not a
complication to be tidied away — it is what a specification looks
like when it stops assuming one implementation.
